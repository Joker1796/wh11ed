# Запись в чейнджлог

Чейнджлог читает игрок: в плашке обновления и на `/changelog`. Пишет его **владелец сайта от
своего лица**, я лишь набираю текст за него. Отсюда все правила ниже.

## 1. Голос

- **Первое лицо единственного числа.** «Я прогнал 1817 списков», «I checked every rule». Не «мы
  прогнали», не «прогнали» без подлежащего, не «команда». Прецеденты — записи про донаты и про
  проверку правил приложения (`grep -n " я \| I " src/data/changelog.js`).
- Там, где действующее лицо не нужно, подлежащее — **сайт или его часть**: «конструктор
  показывает», «списки читаются». Не одушевлять код глаголами вроде «отдала», «научилась»,
  «умеет» — писать, что пользователь может сделать или что видит.
- Обращение к читателю — «вы» / «ваш список», без «пользователь».

## 2. Что писать

- **Только то, что игрок заметит.** Факт → где он это увидит → что теперь иначе. Не как это
  сделано: никаких flex-моделей, регэкспов, гейтов, названий скриптов, коммитов, `ResizeObserver`.
- **Без воды и оценок**: «удобнее», «наконец-то», «значительно», «теперь всё хорошо» — вычеркнуть.
  Один пункт — одно изменение, два-четыре коротких **простых** предложения: без причастных и
  вводных оборотов, без объяснения механики правил («отряд берёт одного Leader и одного
  Support…»), без перечня всех затронутых мест — назвать их через запятую и хватит.
  Прецедент 2026-09-21: запись 2.6.5 пришлось сжать вдвое.
- **Без благодарностей**: строку «Спасибо игроку, который об этом написал» не ставить.
- **Числа — реальные и проверенные**: «1817 списков», «314 листов». Не «около 1800», если известно
  точно, и не точное число, если оно с потолка.
- **Каждое утверждение проверить там, где игрок попробует его первым** (глобальный поиск, а не
  поле на одной странице). Если верно только в одном месте — назвать место явно.
- Формулировки про возможность: «можно добавить / взять / выбрать», не «можно выставлять».
  Формулировки про ограничение: что именно недоступно и **почему это видно** («подсказывает,
  почему»), не «запрещено».
- Имена юнитов, детачментов, стратагем, keywords — по-английски в обеих локалях.

## 2а. Однозначно и просто (владелец, 2026-10-05)

Пункт должен читаться с первого раза и одним смыслом. Если фразу можно понять двумя способами или
её надо перечитать — переписать.

- **Одно предложение — один факт.** Короткие предложения вместо одного длинного с тире,
  точкой с запятой и вставками. Тире-пояснение («— так они берут с собой Deathwatch») — разбить
  на два предложения или выкинуть.
- **Начинать с того, что изменилось для игрока**, а не с причины: «В список Deathwatch больше
  нельзя взять Deathwatch Support. По правилам его берут только…», а не «Deathwatch Support
  напечатан в книге Deathwatch, но по правилам…».
- **Без лишних подробностей и обстоятельств**: где напечатано, почему так вышло, откуда данные,
  «например …», «который доступен этим армиям». Одна причина — если без неё изменение непонятно.
- **«Раньше …» — одно короткое предложение**, только если без него не ясно, что изменилось.
- **Простые слова.** «Есть», «видно», «можно взять», «нельзя». Не «предлагается», «доступен
  для выбора», «собственные детачменты фракции».
- **Проверка вслух**: прочитать RU-пункт целиком. Споткнулся — упростить ещё раз.

Пример (2.7.15). Было: «Deathwatch Support напечатан в книге Deathwatch, но по правилам его могут
взять только Space Marines и другие ордены — так они берут с собой Deathwatch. Раньше конструктор
ростеров предлагал его и спискам Deathwatch. Теперь его предлагают только тем, кому он доступен…»
Стало: «В список Deathwatch больше нельзя взять Deathwatch Support. По правилам его берут только
Space Marines и другие ордены. Его правила по-прежнему есть на странице Deathwatch.»

## 3. Форма

- `changelog[0]` — свежая запись; `version` сверять с `package.json` (скил `release-frontend`
  §2): выше — дописывать в неё, равна — новая запись со следующим патчем.
- Запись = заголовки `{ h: '…' }` + строки-пункты. Заголовок называет поверхность и суть:
  «Конструктор на телефоне: страница стоит на месте». EN и RU **структурно параллельны**:
  заголовок на позиции i в `en` — заголовок на позиции i в `ru`; число пунктов одинаково.
- Типографика: тире `—`, апостроф `’`, кавычки «…» в RU.
- Читаемость проверить голосом: прочитать RU вслух — если предложение спотыкается («не
  переносится на двух строк ни на одном телефоне»), переписать проще («всегда помещается в одну
  строку»).

- **В файле живут только последние 5 релизов.** Более старые `deploy.sh` при выкате переносит
  в архив API (`wh11ed-api`, таблица `changelog`), страница «Что нового» подгружает их по кнопке.
  Править уже ушедшую в архив запись — не в файле: `npm run changelog:publish` в `wh11ed-api` с
  исправленной записью (DEPLOY.md, «Release notes archive»).

## 3а. Кнопки в тексте

Если пункт про новую кнопку или иконку — нарисовать её, а не описывать: `{btn:gear}` рисует
кнопку-иконку, как на экране, `{key:Вернуть}` — кнопку с надписью (надпись — как в `ui.js`).
Имена иконок — в `src/data/changelogMarks.js` (`BTN_ICONS`, с подписью для экранного диктора на
двух языках); новая иконка — строка туда. Метки должны совпадать в EN и RU одного пункта —
`changelogMarks.test.js` это проверяет. Не злоупотреблять: иконка там, где игрок будет её искать.

## 3б. Оформление пункта — всегда одинаково (владелец, 2026-10-13)

- **Каждый пункт об изменении начинается с жирной первой фразы — сути изменения**, целым
  предложением с точкой внутри жирного: `'**Страница запоминает выбранную фракцию.**'`,
  `'**Изменившаяся цена выделена цветом.** Красным, если выросла, зелёным, если упала.'`.
  Остальной текст пункта — обычный. Пункт из одного предложения — жирный целиком.
- Ссылка на юнит может стоять внутри жирного: `'**[Be’lakor](/factions/…) союзником больше не
  обязан быть Warlord.** …'`.
- Жирного внутри остального текста нет — выделяется только суть в начале.
- **Исключения:** раздел «Ответы на вопросы» (вопрос выделяет страница сама — `boldQuestion`) и
  «Спасибо» — там жирного не ставить.
- Одинаково в EN и RU. `changelogMarks.test.js` («opens every change with its gist in bold»)
  падает на пункт без жирного начала — с 2.8.2.

## 3в. Юниты и правила — ссылками (владелец, 2026-10-14, повторено 2026-10-18)

Каждый юнит и каждое правило фракции, названные в пункте, — ссылка, по первому упоминанию в пункте.
Игрок нажимает и сразу видит, о чём речь.

- **Юнит** — `[Nazdreg](/factions/orks/datasheets/nazdreg)`. На странице «Что нового» такая ссылка
  открывает карточку юнита модалкой поверх страницы (`ChangelogView.vue`, `SHEET_LINK`).
  id брать из `src/data/datasheetIndex.js`, не угадывать по имени.
- **Правило** — ссылка на страницу фракции с якорем; страница сама выбирает нужный детачмент:
  - правило армии — `/factions/<slug>#<armyRule.id>`;
  - правило детачмента — `/factions/<slug>#<det.id>-rule`;
  - улучшение — `/factions/<slug>#enh-<det.id>-<slugify(имя)>`;
  - стратагема — `/factions/<slug>#strat-<det.id>-<slugify(имя)>`.

  `slugify` — `src/core/shared/slugify.js`, `det.id` — из `src/data/factions/<slug>.js`.
- Не ссылки: keywords (TECH-PRIEST), оружие, названия детачментов внутри фразы про правило
  («War-form Mantles в Lords of the Forge» — ссылка на War-form Mantles), Combat Patrol-правила без
  страницы фракции.
- Ссылки одинаковые в EN и RU одного пункта. Вопрос в «Ответах на вопросы» ссылкой не делать —
  ссылки в ответе.

## 4. Перед коммитом

```bash
node -e "import('./src/data/changelog.js').then(m => console.log(m.changelog[0].version))"
npx vitest run src/composables/useUpdateNotice src/data/changelogMarks
```

Показать пользователю RU-текст целиком — он читает и правит стиль сам; коммит только после
его «ок».
