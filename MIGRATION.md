## Финал (endgame)

**Один домен — и в конце буквально один.** `wh-rules.ru` становится основным; `wh11ed.ru` уходит
в 301 **на ограниченный срок**, после чего отключается ПОЛНОСТЬЮ: CDN, бакеты, сертификаты, зона,
домен не продлевается.

**Решение владельца 2026-08-26 — осознанное, с известными последствиями.** Раньше здесь стояло
«постоянный 301, бессрочно — ради ссылок и SEO-веса». Отменено: проект открытый, без спонсоров,
вся инфраструктура за личные деньги, и платить за вечную редирект-заглушку нерационально, каким бы
копеечным ни был тариф. База пользователей оповещена (баннер `pre` на замороженном `wh11ed.ru`
плюс автосинк). Ниже записано, чем мы за это платим, — чтобы через полгода не выяснять заново и не
принимать это за недосмотр:

- **HSTS-стена.** Старый домен год отдавал `Strict-Transport-Security: max-age=31536000`. После
  отключения браузер у всех, кто там был, продолжит принудительно требовать HTTPS и покажет ошибку
  сертификата **без кнопки «всё равно перейти»** — до истечения max-age от их последнего визита.
  Ничем, кроме времени, не лечится.
- **Ссылочный вес.** 301 передаёт вес, только пока отвечает. После отключения внешние ссылки на
  `wh11ed.ru` становятся битыми, накопленный вес теряется целиком.
- **Старые закладки и установленные PWA** со старым origin умирают окончательно.

Отсюда единственное, что остаётся обязательным: **301 должен пожить достаточно, чтобы переезд
успел засчитаться** (Change of Address + переиндексация), и только потом рубим. Порядок и условия —
Фаза 4.

**Решение 2026-08-15: бэкенд стал host-aware** (одна функция обслуживает оба api-домена,
`siteForHost()` в `wh11ed-api/src/config.ts` выводит cookieDomain/redirect/after-login из `Host`
запроса; неизвестные хосты падают на env-дефолты). Это НЕ отменяет финал «один домен + 301» —
host-aware нужен, чтобы логин работал на `wh-rules.ru` уже в грейс-период и люди могли переезжать
органически. Второй бэкенд/вторая база по-прежнему НЕ наш путь. Проверено по докам Яндекса:
API Gateway передаёт функции оригинальный user-facing `Host` (docs functions/concepts/
function-invoke), у OAuth-приложения зарегистрированы ОБА redirect_uri.

## Почему фазово, а не одним катовером (технические ограничения, диктующие темп)

1. **(Снято host-aware бэкендом, см. выше.)** Исторически: статичные env `cookieDomain`/
   `APP_AFTER_LOGIN_URL`/`redirect_uri` привязывали логин к одному домену, и Strict-кука в
   cross-site запросе убивала сессию через ~15 мин. С host-aware функцией (после её деплоя)
   логин работает на обоих доменах: каждый api-хост выставляет куку и redirect_uri под себя.
   До деплоя функции ограничение ещё действует.
2. **Локальные игры привязаны к origin.** Трекер хранит партии в `localStorage` origin'а
   `wh11ed.ru` (`useTracker.js`). После 301 несинканные локальные игры станут **недоступны** —
   браузер не отдаёт их для другого origin. → их надо успеть синкнуть в облако ДО переезда.
3. **Облачные игры — общие, копировать не надо.** Синканные партии лежат в одной YDB по
   `userId = yandex:<sub>` (тот же на любом домене, OAuth-приложение одно). После переключения
   они **сами подтянутся** на новом домене. База одна — никакого копирования между доменами.
4. **Установленные PWA origin-locked.** После 301 их service worker отдаёт кэш офлайн, приложение
   **не обновляется**, логин ломается. Достучаться до таких юзеров можно только **пока они ещё
   ходят в сеть** (до 301) — предупредить «переустанови с нового домена».
5. **Автосинк помогает только залогиненным.** Логин опциональный; большинство юзеров, вероятно,
   НЕ авторизованы — их локальные игры автосинк не спасёт (в облаке их нет). Реальный
   предохранитель для этой массы — **баннер-подсказка** «залогинься и синкни».

## Фазы

### Фаза 0 — Автосинк ✅ СДЕЛАНО (задеплоено, v2.0.19) — чистый фронт, без бэка
Реализовано: при входе в трекер, если юзер `authed`, идёт полный `syncNow()` (`TrackerHomeView.vue`
onMounted) — заливает старый бэклог **и** тянет облачные игры в локальную историю. Новые игры
сессии и так лились сами (`watch(history)` в `useCloudSync.init()`); убран лишний флаг
`SYNC_AFTER_LOGIN`. `syncNow` тянет облако в локальную историю (восстановление) — для миграции это
желаемо, удаления защищены tombstone'ами.
Задеплоено на **оба** домена через `./deploy-both.sh`. Заодно в Фазе 0 закрыли SEO-гигиену:
статические теги `index.html`/`robots.txt` теперь тоже по `VITE_SITE_ORIGIN` (грейс → canonical
`wh11ed.ru` на обоих доменах, дубль-контента нет).

### Фаза 1 — Ждём ~неделю ✅ ПРОЙДЕНА
Залогиненные юзеры за неделю накапливают игры в облаке (общая YDB) автоматически. Прод не трогаем.

### Фаза 2 — Баннер «переезжаем» + ждём ~неделю ✅ СДЕЛАНО (v2.2.6, 2026-08-15)
Включить баннер на `wh11ed.ru`: `VITE_ANNOUNCE_MOVE=pre` в `.env.deploy.wh11ed`
(`DomainMoveBanner.vue` + `config.js`). **Текст фазы (pre-switch, реализован):** «сайт переезжает
на wh-rules.ru» (домен кликабелен для удобства, но CTA нарочно ведёт в /tracker ЗДЕСЬ: логин на
новом домене ещё не работает) + «залогинься — сохранённые партии переедут с тобой» +

- Обе фазовые версии текста в коде: `VITE_ANNOUNCE_MOVE=pre` (эта) и `=moved` (post-301

## Механика деплоя

Одна цель — `wh-rules.ru`. `npm run deploy` берёт gitignored `.env.deploy`:

| Файл | BUCKET | CDN | `VITE_SITE_ORIGIN` | `VITE_API_BASE_URL` |
|---|---|---|---|---|
| `.env.deploy` (рабочий) | `s3://wh-rules.ru` | `bc8r6sdaw3f64oi3hbdo` | `https://wh-rules.ru` | `https://api.wh-rules.ru` |
| `.env.deploy.wh11ed` (заморожен, откат) | `s3://wh11ed.ru` | `bc8raqgpcdeagfb6ygn6` | `https://wh11ed.ru` | `https://api.wh11ed.ru` |

`VITE_SITE_ORIGIN` — единственный рубильник домена: он гонит runtime canonical/hreflang
(`useSeoMeta`), sitemap, `robots.txt` (генерится в `gen-seo-routes.mjs`) И статические теги
`index.html` (og/twitter/JSON-LD, через плейсхолдер `%SITE_ORIGIN%` + плагин в
`vite.config.js`). Ручных правок index.html/robots на катовере НЕТ.

`api.wh-rules.ru` обслуживается той же host-aware функцией, что и `api.wh11ed.ru` — логин
работает на обоих хостах.

## Финальный катовер (Фаза 3) — runbook

**Порядок строгий: бэк ПЕРВЫМ, потом 301.** Фронтовая часть шага 2 уже сделана (новый домен
канонический с 2026-08-16); осталось решить, надо ли ещё раз тронуть замороженный старый домен
ради post-301 текста баннера — по-хорошему не надо, 301 всё равно уводит с него.

1. **Бэк → wh-rules.ru** — ✅ **сделано 2026-08-26** (версия функции `d4e4j70m906uo3tk1q3v`).
   Terraform для этого больше НЕ используется: стейт потерян, `apply` с пустого стейта попытается
   пересоздать 11 ресурсов, включая YDB с партиями и листами. Деплой — `bash scripts/deploy.sh`
   в `wh11ed-api` (копирует конфиг живой версии, переопределения — в гитигноренном `deploy.env`).
   С host-aware функцией это меняет только **env-дефолты** (fallback для неизвестных Host) —
   логин на обоих доменах работает и до, и после. Важная мелочь: `corsOrigin()` отдаёт ПЕРВЫЙ
   origin из `ALLOWED_ORIGINS` как канонический, поэтому `wh-rules.ru` стоит там первым.
   `api.wh11ed.ru` пока оставлен привязанным (легаси-PWA), снимается в Фазе 4.
2. **Фронт** — ✅ уже сделано 2026-08-16: `VITE_SITE_ORIGIN=https://wh-rules.ru` в `.env.deploy`,
   релизы идут только туда. Старый домен трогать не нужно (он под 301).
3. **Проверка:** `curl -sI https://wh-rules.ru/` (200), логин + облачный синк на wh-rules.ru.
4. **301 старого домена** (`yc`, доступ есть):
   ```bash
   yc storage bucket update wh11ed.ru --website-settings \
     '{"redirect_all_requests":{"protocol":"PROTOCOL_HTTPS","hostname":"wh-rules.ru"}}'
   yc storage bucket update www.wh11ed.ru --website-settings \
     '{"redirect_all_requests":{"protocol":"PROTOCOL_HTTPS","hostname":"wh-rules.ru"}}'
   yc cdn cache purge --resource-id bc8raqgpcdeagfb6ygn6 --all   # старый CDN
   ```
