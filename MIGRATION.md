# Курс: переезд `wh11ed.ru` → `wh-rules.ru` (фазовая миграция)

> **ЭТО ИСТОЧНИК ПРАВДЫ по миграции домена.** Обе рабочие машины видят этот файл через git.
> Локальная память Claude между машинами НЕ синхронизируется — в новой сессии на любой машине
> сверяться отсюда, а не с памяти. Память лишь ссылается сюда.
>
> **Текущая фаза: Фаза 1 (грейс-период, ждём).** Фаза 0 задеплоена (v2.0.19): автосинк и
> env-driven SEO-грейс живут в проде на обоих доменах. Живой прод — `wh11ed.ru`, полностью
> рабочий (включая логин). `wh-rules.ru` — вспомогательный, логин там пока не работает (см. ниже).
> Следующее активное действие — Фаза 2 (баннер) после грейс-периода.

---

## Финал (endgame)

**Один домен.** `wh-rules.ru` становится основным; `wh11ed.ru` → **постоянный 301** на него
(бессрочно — ради старых ссылок, закладок и SEO-веса). Старый домен уходит в редирект.

Из этого следует важное: **не нужен ни второй бэкенд, ни host-aware бэкенд.** На финальном шаге
бэк просто перенастраивается (env-переменные) на `wh-rules.ru`. Вся возня про «два параллельных
бэка / две базы» — НЕ наш путь.

> ⚠️ Если решение изменится на «оба домена живут параллельно навсегда» — это ДРУГОЙ финал: тогда
> нужен host-aware бэкенд (cookieDomain/redirect/after-login из Host запроса) и 301 НЕ делаем.
> Подтвердить финал до начала Фазы 3.

---

## Почему фазово, а не одним катовером (технические ограничения, диктующие темп)

1. **Один статичный бэкенд обслуживает логин только ОДНОГО домена.** `cookieDomain`,
   `APP_AFTER_LOGIN_URL`, `redirect_uri` — статичные env (`wh11ed-api/src/config.ts`). Плюс
   refresh-кука пере-выставляется `SameSite=Strict` (`routes/auth.ts`), а Strict-кука **не
   отправляется в cross-site запросе** → если новый домен ходит в чужой api, логин заведётся, но
   отвалится через ~15 мин (первая ротация токена). Значит логин на `wh-rules.ru` реально
   заработает только когда бэк туда флипнется (финальный шаг).
2. **Локальные игры привязаны к origin.** Трекер хранит партии в `localStorage` origin'а
   `wh11ed.ru` (`useTracker.js`). После 301 несинканные локальные игры станут **недоступны** —
   браузер не отдаёт их для другого origin. → их надо успеть синкнуть в облако ДО переезда.
3. **Облачные игры — общие, копировать не надо.** Синканные партии лежат в одной YDB по
   `userId = yandex:<sub>` (тот же на любом домене, OAuth-приложение одно). После переключения
   они **сами подтянутся** на новом домене. База одна — никакого копирования между доменами.
4. **Установленные PWA origin-locked.** После 301 их service worker отдаёт кэш офлайн, приложение
   **не обновляется**, логин ломается. Достучаться до таких юзеров можно только **пока они ещё
   ходят в сеть** (до 301) — предупредить «переустанови с нового домена».
5. **Автосинк помогает только залогиненным.** Логин опциональный; большинство юзеров, вероятно,
   НЕ авторизованы — их локальные игры автосинк не спасёт (в облаке их нет). Реальный
   предохранитель для этой массы — **баннер-подсказка** «залогинься и синкни».

## Фазы

### Фаза 0 — Автосинк ✅ СДЕЛАНО (задеплоено, v2.0.19) — чистый фронт, без бэка
Реализовано: при входе в трекер, если юзер `authed`, идёт полный `syncNow()` (`TrackerHomeView.vue`
onMounted) — заливает старый бэклог **и** тянет облачные игры в локальную историю. Новые игры
сессии и так лились сами (`watch(history)` в `useCloudSync.init()`); убран лишний флаг
`SYNC_AFTER_LOGIN`. `syncNow` тянет облако в локальную историю (восстановление) — для миграции это
желаемо, удаления защищены tombstone'ами.
Задеплоено на **оба** домена через `./deploy-both.sh`. Заодно в Фазе 0 закрыли SEO-гигиену:
статические теги `index.html`/`robots.txt` теперь тоже по `VITE_SITE_ORIGIN` (грейс → canonical
`wh11ed.ru` на обоих доменах, дубль-контента нет).

### Фаза 1 — Ждём ~неделю ⏳ ТЕКУЩАЯ
Залогиненные юзеры за неделю накапливают игры в облаке (общая YDB) автоматически. Прод не трогаем.

### Фаза 2 — Баннер «переезжаем» + ждём ~неделю
Включить баннер на `wh11ed.ru`: `VITE_ANNOUNCE_MOVE=pre` в `.env.deploy.wh11ed`
(`DomainMoveBanner.vue` + `config.js`). **Текст фазы (pre-switch, реализован):** «сайт переезжает
на wh-rules.ru» (домен кликабелен для удобства, но CTA нарочно ведёт в /tracker ЗДЕСЬ: логин на
новом домене ещё не работает) + «залогинься — сохранённые партии переедут с тобой» +
«установленное приложение потом переустанови с нового адреса». Это главный предохранитель для незалогиненных
и единственный шанс достучаться до PWA-юзеров (пока их SW ходит в сеть).
- Обе фазовые версии текста в коде: `VITE_ANNOUNCE_MOVE=pre` (эта) и `=moved` (post-301
  «мы переехали», ссылка на новый домен; легаси-значение `true` = `moved`). Дисмисс у фаз
  раздельный (`wh11ed-domain-move-dismissed[-pre]`) — закрытие pre-баннера не спрячет post-301.

### Фаза 3 — Финальный катовер (301) — подтвердить финал перед стартом
Бэк-катовер ПЕРВЫМ, потом фронт, потом 301. Полный runbook — ниже. Мы это уже один раз прошли и
откатили (2026-07-20), процедура и подводные камни известны.

## Механика деплоя на оба домена

`deploy.sh` принимает `ENVFILE` (какой конфиг взять). `deploy-both.sh` катит **один релиз на оба
домена** одним прогоном: bump версии один раз, затем `wh-rules.ru` (канарейка, мало трафика) →
`wh11ed.ru` (живой прод — вторым, чтобы упавший деплой канарейки не задел юзеров). Каждый домен —
свой gitignored `.env.deploy.<name>`:

| Файл | BUCKET | CDN | `VITE_SITE_ORIGIN` | `VITE_API_BASE_URL` |
|---|---|---|---|---|
| `.env.deploy.wh11ed` | `s3://wh11ed.ru` | `bc8raqgpcdeagfb6ygn6` | `https://wh11ed.ru` | `https://api.wh11ed.ru` |
| `.env.deploy.wh-rules` | `s3://wh-rules.ru` | `bc8r6sdaw3f64oi3hbdo` | `https://wh11ed.ru`¹ | `https://api.wh-rules.ru`² |

¹ **Грейс-период:** `wh-rules.ru` печёт canonical → `wh11ed.ru`, чтобы не дробить SEO (дубль-контент).
На Фазе 3 флипается на `https://wh-rules.ru`. `VITE_SITE_ORIGIN` — единственный рубильник домена:
он гонит runtime canonical/hreflang (`useSeoMeta`), sitemap, `robots.txt` (генерится в
`gen-seo-routes.mjs`) И статические теги `index.html` (og/twitter/JSON-LD, через плейсхолдер
`%SITE_ORIGIN%` + плагин в `vite.config.js`). Ручных правок index.html/robots на катовере НЕТ.
² `wh-rules.ru` печёт свой api заранее — после бэк-катовера логин там заработает без пересборки.
До Фазы 3 логин на `wh-rules.ru` не работает (кука выставится на `api.wh11ed.ru`), но
правила/трекер/просмотр — полностью рабочие.

## Финальный катовер (Фаза 3) — runbook

**Порядок строгий: бэк ПЕРВЫМ, потом фронт, потом 301.**

1. **Бэк → wh-rules.ru** (`PhpstormProjects/11/wh11ed-api/infra`, там state):
   `terraform apply -target=yandex_function.api -var api_base_url=https://api.wh-rules.ru
   -var app_after_login_url=https://wh-rules.ru/tracker/auth-callback -var cookie_domain=api.wh-rules.ru`.
   `api.wh11ed.ru` оставить привязанным (легаси-PWA). OAuth redirect_uri — оба уже есть.
2. **Фронт** (`.env.deploy.wh-rules` → `VITE_SITE_ORIGIN=https://wh-rules.ru`; в
   `.env.deploy.wh11ed` баннер переключить на `VITE_ANNOUNCE_MOVE=moved` — post-301 текст),
   `./deploy-both.sh` → обе сборки на оба бакета.
3. **Проверка:** `curl -sI https://wh-rules.ru/` (200), логин + облачный синк на wh-rules.ru.
4. **301 старого домена** (`yc`, доступ есть):
   ```bash
   yc storage bucket update wh11ed.ru --website-settings \
     '{"redirect_all_requests":{"protocol":"PROTOCOL_HTTPS","hostname":"wh-rules.ru"}}'
   yc storage bucket update www.wh11ed.ru --website-settings \
     '{"redirect_all_requests":{"protocol":"PROTOCOL_HTTPS","hostname":"wh-rules.ru"}}'
   yc cdn cache purge --resource-id bc8raqgpcdeagfb6ygn6 --all   # старый CDN
   ```
5. **Google Search Console (ТЫ):** добавить wh-rules.ru, Change of Address, пересабмитить sitemap.

**Откат** (проверен 2026-07-20): бакеты wh11ed.ru/www обратно в index/error; бэк-функция обратно на
env wh11ed.ru; `api.wh11ed.ru` и так привязан. Старый cert `fpq9e4a2f8s5e6812slm` специально НЕ
удаляли — жив, поэтому откат быстрый.
