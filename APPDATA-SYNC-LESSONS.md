# wh40k-appdata reconciliation — lessons learned

Reusable diagnostic patterns from the full wh11ed-vs-`wh40k-appdata` datasheet/faction-rules
reconciliation (all 30 factions, closed and merged 2026-07-27, PR #264). Read this before starting
any future re-sync (e.g. after an appdata `data_version` bump) — it saves re-deriving the same
false-positive/false-negative classes from scratch. Not a substitute for reading the current code
and appdata state fresh; a data model can change between now and when this is next read.

1. **appdata sometimes contradicts itself**: if a structural field (`wargear[].name`, `keywords`,
   `leaderOf`) disagrees with the prose of the same datasheet (`unitComposition`/`wargearRules`) —
   trust the structural field. The prose is what typically has the typo.
2. **appdata has real OCR/typo defects** — "Grimaidus", "cenabyte", "Martial Examplars",
   "automically", "af"→"of", doubled words, etc. Don't copy these into wh11ed.
3. **`type:'image'` blocks** in `rules[].body[]` are tables/graphics from the book that appdata
   didn't digitize. wh11ed transcribes the same thing as text — not a bug if the numbers agree.
4. **SM-Chapter factions** (black-templars/blood-angels/dark-angels/deathwatch/space-wolves): a huge
   "extra in wh11ed: datasheet …" list is not missing data — the shared `space-marines.js` pool
   lives in `adeptus-astartes.json` separately from the Chapter's own bundle. Same logic for the
   Oath of Moment army rule (a Chapter bundle carries only a stub pointer, or nothing at all).
5. **Merged-profile units** (one `profiles[]` row in appdata standing for several same-stat models)
   — with >1 profile on a datasheet, strict name-matching false-negatives the statline. Verify by
   comparing the numbers by hand, not the name.
6. **Per-profile baseSize check stays silent** (no diff reported) when the wh11ed profile name
   doesn't text-match a line in appdata's `baseSize` string — "clean" on this field doesn't mean
   actually clean; manually `node -e` merged-profile datasheets.
7. **Number words vs digits** ("one"/"5" vs "1"/"five") and the **"1 <Name> — EPIC HERO" prefix** —
   a deliberate wh11ed house style (digits almost everywhere; "one of the following" is a settled
   idiom, 471 occurrences vs 6 "1 of the following"). Don't change these to match appdata.
8. **A "KEYWORDS" tail inside a rule body** can be either (a) a pure duplicate of
   `conditionalKeywords.json` (then delete it — precedents: Masters of Manoeuvre, The Lost Brethren,
   Dêlve Assault Shift) or (b) a mixed block with real content that exists nowhere else in appdata
   (then leave it — precedent: Houndpack Lance "Marked Prey", the same class as Deathwatch's
   "Restrictions written into the rule body because there's nowhere else to put it"). Check
   `conditionalKeywords.json` line by line — don't delete the whole block on sight.
9. **A detachment's Restrictions text isn't guaranteed for every detachment in a faction at once** —
   check the specific detachment via `node -e`, don't assume it's faction-wide.
10. **Several appdata `armyRules[]`/`rules[]` cards get merged into one wh11ed field** (appdata
    prints 2-3 separate cards where wh11ed's data model has room for one armyRule/rule per
    faction/datasheet) — the sync script falsely screams "wh11ed adds" for everything after the
    first card. Precedents: titan-legions/chaos-titan-legions (Towering Example + Titanic Support +
    Titanicus Traitoris), chaos-knights (Harbingers of Dread + Dreadblades + Super-heavy Walker).
    Verify by hand against the exact appdata JSON — don't trust the diff at a glance.
11. **`src/data/sourceIds.json`** — the stable uuid bridge wh11ed↔appdata (`kind:
    armyrule|det|strat|enh|ds|wg`), regenerated by `node scripts/gen-source-ids.mjs`. Don't hand-edit.
12. **Local `sources/Faction pack 11 ed/*.pdf` files can be STALE versions.** A verbatim match
    against a local PDF in `sources/` proves nothing about the current rules — that file itself may
    be an old edition. **appdata is canon** for rules wording (the MFM is secondary — points/DP/
    disposition only). To check against an official source directly, download a FRESH Faction Pack
    from `warhammer-community.com/en-gb/downloads/warhammer-40000/` (see lesson 14) — don't treat a
    local `sources/*.pdf` as ground truth.
13. **Before declaring a piece of text "drift because it's not in appdata" — check
    `../wh40k-appdata/tables/*.json` (the full relational DB), not just the flat
    `../wh40k-appdata/factions/<slug>.json` export.** The flat export does NOT include: ally
    inclusion (who can take whom as an ally and at what points threshold — `allied_faction`,
    `allied_faction_required_detachment`, `allied_faction_points_limit`,
    `allied_faction_parent_faction_keyword`, `allied_faction_keyword`), enhancement-attach/bodyguard
    groups (`enhancement_bodyguard_group`, `_datasheet`, `_keyword`), roster-composition limits by
    keyword (`restriction_group_detachment_limit` — `minRosterLimit`/`maxRosterLimit` tied to
    `keyword_restriction_group`/`keyword_restriction_group_keyword`, i.e. "the army must include 3+
    units with keyword X"), datasheet exclusions (`detachment_excluded_datasheet` — "can't include
    datasheets Y/Z"), a detachment's own **Restrictions/Keywords card-box text**
    (`detachment_detail` + `detachment_detail_bullet_point` — see lesson 21, found only *after* the
    original 30-faction pass closed), and datasheet-level Leader/Support attach requirements
    (`enhancement_required_keyword_group` + `_faction_keyword`/`_keyword` — "model only" restrictions
    on an enhancement), plus some keyword grants beyond what already made it into
    `conditionalKeywords.json` (`conditional_keyword.json` itself is richer than what the generator
    `gen-conditional-keywords.mjs` pulls from it — see its own comment in `CLAUDE.md`: it only takes
    roster-faction-keyword and detachment grants, skipping per-unit allegiance grants). General
    method: find the entity's id (`factions/<slug>.json` gives a detachment/datasheet/enhancement
    id), then grep `tables/` for that id as an FK (`detachmentId`, `enhancementId`, `datasheetId`),
    resolving related ids through `keyword.json`/`faction_keyword.json`/`battle_size.json` etc.
    **Don't stop at the first empty/non-empty table** — an entity's data can be spread across
    several tables at once (see the Houndpack Lance precedent below, where checking only one table
    first gave a false "not found").
    **Precedent (worked out over one commit, revisited three times):**
    - emperors-children: first wrongly deleted the Legions of Excess ally text in "Daemonic
      Empowerment" and an attach clause in "Exalted Patron" as "unconfirmed" (not found in
      `factions/emperors-children.json`) — both turned out to be clearly confirmed in `tables/`:
      Legions of Excess via `allied_faction` (id `e94941b5-…`) → `allied_faction_points_limit`
      (500/1000/1500 by `battleSizeId`) → `allied_faction_parent_faction_keyword` →
      `faction_keyword.json` = "Legions of Excess"; Exalted Patron's attach via
      `enhancement_bodyguard_group` (`bodyguardType:'leader'`) →
      `enhancement_bodyguard_group_datasheet` → datasheet = "Flawless Blades". Both restored.
      Fulgrim's "Serpentine" ability was checked the same way via the
      `datasheet_datasheet_ability` join (all 5 of the datasheet's abilities listed explicitly,
      Serpentine isn't among them) — this one really is gone, stayed deleted.
    - chaos-knights "Houndpack Lance" · KEYWORDS block (3+ War Dog units required, they gain
      Battleline; 3 chosen ones gain Character) — the Battleline grant was found immediately via
      `conditional_keyword` (6 rows, `requiredDetachmentId` = Houndpack Lance, `keywordId` =
      "Battleline"). The "3+ War Dog" requirement was **missed on the first pass** (only checked
      `detachment_required_datasheet` — empty) and nearly got left as "partially unconfirmed"; a
      more careful check found yet ANOTHER table — `restriction_group_detachment_limit`
      (`minRosterLimit: 3`, `detachmentId` = Houndpack Lance) → `keyword_restriction_group` →
      `keyword_restriction_group_keyword` = "War Dog". The whole block ended up fully confirmed by
      appdata, no external source needed.
    The only legitimate reason to keep content that never surfaces in the flat
    `factions/<slug>.json` is either corroboration from appdata ITSELF (lesson 3 — a `type:'image'`
    block in the same spot; lesson 10 — the text sits under a separate card of the same JSON; this
    lesson — found in `tables/`, but check SEVERAL candidate tables, not just one), or, as a last
    resort when appdata truly is silent, a verbatim match against a JUST-downloaded (not local!)
    official PDF — see lesson 14.
14. **If content shows up in neither the flat JSON nor `tables/` (after an honest attempt — see
    lesson 13) — download the current Faction Pack/Index/Codex PDF straight from
    `warhammer-community.com`** (links on `/en-gb/downloads/warhammer-40000/`; search via web search
    for `<faction> Faction Pack pdf warhammer-community.com`, `curl` it into a scratch dir, read
    with `pdftotext -layout`) and check against it directly. This is NOT the same as lesson 12 (a
    local, potentially stale file) — a fresh download from the official site is a valid source that
    supplements appdata, not one that replaces it as canon.
    Precedent: deathwatch "Black Spear Task Force" · Mission Tactics `Restrictions:` block — appdata
    confirms PART of it structurally (`detachment_excluded_datasheet` + a duplicating
    `faction_keyword_excluded_datasheet`: 9 excluded datasheets — 5 resolve to Tactical/Terminator/
    Devastator/Scout Squad + Terminator Assault Squad, 4 more in `agents-of-the-imperium.json` =
    Watch Master/Watch Captain Artemis/Corvus Blackstar/Deathwatch Kill Team, i.e. the structural
    implementation of "no Agents of the Imperium Deathwatch units"). **Not everything — but not
    because the search was shallow; a CATEGORICAL source boundary showed up:** the remaining ~7
    banned units (Assault Squad, Attack Bike Squad, Land Speeder Storm, Relic Terminator Squad,
    Scout Bike Squad, Scout Sniper Squad) are **Legends** units; the schema has a
    `datasheet.isLegends` field, but in the raw `tables/datasheet.json` (1142 rows) it is **`false`
    for every single one** — this slice of appdata carries no Legends content for any faction at
    all, so a nonexistent datasheet can't be structurally excluded. Likewise no mono-Chapter
    restriction turned up — checked all 16 `keyword_restriction_group` rows, none reference the
    faction_keyword "Deathwatch"; this looks like an implicit rule (Army Faction = Deathwatch
    already restricts datasheet choice) that the book just states explicitly rather than encoding
    as its own DB row. **Conclusion:** for Legends units and implicit rules, digging further in
    `tables/` is pointless — this isn't "one more table," the whole category is absent; here a
    freshly-downloaded official PDF is the only practical check. Verified verbatim against
    `eng_08-06_..._faction_pack_deathwatch...pdf`, left unchanged.
15. **For the future: appdata might one day start including Legends datasheets**
    (`datasheet.isLegends` already exists in the schema, currently just `false` for all 1142 rows —
    the source doesn't track them yet, but the field is reserved, i.e. this is a question of an
    appdata data update, not a permanent architectural limit). If/when that happens (visible via
    `npm run sync`: `sourceIds.json`/the structural diff suddenly finding datasheets like "Assault
    Squad"/"Attack Bike Squad"/"Land Speeder Storm" where there used to be a gap) — **pick them up**
    like any other structural sync finding (check the datasheet, add/verify it in
    `src/data/datasheets/<slug>.js`, refresh `sourceIds.json` via `gen-source-ids.mjs`). **Until
    then, the usual convention holds: "not in appdata — not in ours"** — don't add Legends
    datasheets as full entries on your own (from a fresh PDF or personal GW knowledge), even knowing
    the unit exists in the rules. Restrictions text that merely *mentions* a Legends unit by name
    (as with Deathwatch above) can stay as prose — that's not the same as adding the datasheet itself.
16. **Numeric "badges" (thresholds/limits printed on the card as a standalone icon/digit rather than
    ordinary sentence text) systematically vanish during appdata extraction, even when the rest of
    the same rule's text is extracted in full.** Three independent precedents in a row:
    thousand-sons "Cabal of Sorcerers" (Warp Charge 5/6/7/9 across four rituals — appdata knows only
    the ritual by name, no numbers at all); grey-knights "Gate of Infinity" (the "how many units by
    battle size" table — 2/3/4 — is missing entirely, not even as a `type:'image'` placeholder);
    world-eaters "Blessings of Khorne" (double 1+/2+/3+/4+/5+/6 across six Blessings — appdata knows
    the names and effects but not the thresholds). Distinguish from lesson 3 (`type:'image'` —
    appdata honestly flags there's a table there, it just didn't digitize it) — here appdata usually
    leaves **no trace at all** that a number was ever there, neither as an `image` block nor as
    text. Where possible, verify at least one data point through side evidence (Warp Blades'
    "double 5+" was confirmed by an example inside a `type:'quote'` of the same rule) — if even one
    point checks out and the rest form a sensible increasing/legible sequence, there's no extra
    reason to worry. **Don't delete or zero out** such numbers just because appdata doesn't have
    them — without them the ability is non-functional, and the sequence itself (not a lone number)
    is usually distinctive enough not to be a wh11ed invention.
17. **appdata doesn't track every allied faction as its own file — if that file simply doesn't
    exist, all content about that ally faction appearing inside the main faction's detachments is
    impossible to re-verify in principle** (not "searched poorly" — a categorical gap, like lesson
    14's Legends case, but at the level of a whole faction rather than one field). Precedent:
    aeldari — `wh40k-appdata/factions/` contains neither `harlequins.json` nor `ynnari.json`, nor a
    separate file for Corsairs/Anhrathe (while `asuryani.json`, the main aeldari faction, does
    exist). Detachments describing these allies' mechanics (Ghosts of the Webway/Serpent's Brood —
    Harlequins Troupe Battleline + OC2 + unique-model limit + the ACROBATIC tag; Devoted of Ynnead —
    mandatory Yvraine/The Yncarne inclusion + warlord; Eldritch Raiders/Corsair Coterie — a Corsair
    Enhancement points surcharge) show up as "wh11ed adds, appdata is silent" — but appdata simply
    can't know about a faction it doesn't store at all. If the content is substantive, internally
    consistent, and doesn't look invented — leave it; unlike Legends (where "not in appdata — not
    in ours" still applies, because appdata KNOWS the category and just didn't fill the field), this
    is a different kind of gap — the source doesn't cover the ally faction at all. Check `ls
    wh40k-appdata/factions/` in future if in doubt — does this ally faction even have its own file —
    before deleting anything that looks like this.
18. **Wargear "containers" whose own name NEVER matches the name of the weapon they grant — 
    `sync-appdata.mjs` will forever report them as a false extra/missing pair.** Precedent:
    tau-empire drones — `Gun Drone` (the wargear item's name) grants `Twin pulse carbine` (a
    completely different name), `Missile Drone` → `Missile pod`, `Recon Drone` → `Drone burst
    cannon`, `MV15 Gun Drone` → `Twin pulse blaster`. appdata stores this as `wargear[].ruleText:
    "The bearer is equipped with the following ranged weapon:"` plus a nested `profiles[]` under a
    different name. The script compares by the container's literal top-level name, so even when
    everything is correctly set up (matching the nested profile's name) it will keep shouting
    "missing: Gun Drone" / "extra: Twin pulse carbine". Check by hand: if a unit's `options[]`
    mentions a drone and `ranged[]` has a similarly-statted weapon under a different name, cross-
    check via `ds.wargear.find(w=>w.name==="Gun Drone").profiles` in appdata — don't trust the bare
    name in the diff.
19. **A statically hard-coded, conditionally-granted keyword is a real bug, not a false positive —
    hunt for it via EN/RU parity, not just the appdata diff.** Precedent: chaos-daemons —
    `"Shadow Legion"` sat in `keywords[]` on **41 datasheets** (almost the whole file), appdata
    doesn't know it there for any unit at all, and the "Shadow Legion" detachment's own text plainly
    says "Legiones Daemonica units from your army gain the SHADOW LEGION keyword" — i.e. the grant
    is conditional (only when that detachment is selected), the `conditionalKeywords.json` pattern —
    but it showed up as a hard-coded string on EVERY unit instead. The tell that flagged the bug
    before even reading appdata: the RU file didn't have that word once (0 of 41) — static drift at
    that scale almost always either breaks EN/RU parity or came from one careless bulk-add. If
    `sync-appdata.mjs` reports the same "extra keyword" on DOZENS of datasheets at once, that's not
    noise, that's a copy-paste bug — check the RU-file count first.
20. **Numeric badges also hide behind non-image tables** — same failure mode as lesson 16, worth
    keeping in mind as its own reminder alongside the other numeric-badge precedents when a rule's
    prose is complete but a number that should logically be there (a threshold, a roster count, a
    points bracket) simply isn't anywhere in appdata: check side evidence (an example inside a
    `type:'quote'`, an internally consistent increasing sequence) before assuming fabrication.
21. **A whole extra appdata table pair can be missed for an entire multi-week project:**
    `tables/detachment_detail.json` (`{id, detachmentId, localisations.en.title}` — usually
    "Restrictions"/"Keywords", sometimes a named block like "Thralls of the First Prince" or
    "HARLEQUINS") + `tables/detachment_detail_bullet_point.json`
    (`{detachmentDetailId, displayOrder, localisations.en.text}`) carry each detachment's
    Restrictions/Keywords card-box text — content the flat `factions/<slug>.json` export's
    `rules[].body` **never** includes. Every "appdata says nothing" conclusion the original
    30-faction pass reached for this specific kind of content (mono-Chapter restrictions,
    Battleline/Character keyword-grant paragraphs, ally-inclusion clauses) was checked against an
    incomplete source. Found this way, previously invisible: 4 blood-angels detachments + 5
    dark-angels detachments + 3 black-templars detachments + 4 space-wolves detachments missing
    their mono-Chapter "Restrictions:" paragraph entirely (some also missing a "Keywords:"
    Battleline-grant paragraph); space-marines' Headhunter Task Force and adeptus-custodes' Solar
    Spearhead had Designer's-Note formatting bugs. **This table is still not exhaustive** — several
    detachments (blood-angels' Legacy of Grace/Encarmine Speartip/Wrath of the Doomed, dark-angels'
    Dark Age Arsenal/Darkflight Pursuit/Interrogation Conclave) correctly carry this text in wh11ed
    despite having **no** row in `detachment_detail` at all — so absence from this table is *not*
    proof content is fabricated either; cross-check sibling detachments in the same file (do they
    share a `daOnly`/`chapterLock`-style constant? are some call-sites of it missing?) before
    concluding a gap is real or fake. A guardrail now exists —
    `scripts/sync-detachment-details.mjs`, wired into `npm run sync` — so this specific class of
    drift can't hide again unnoticed; **check this table pair FIRST** on any future full re-sync,
    before the flat export, to catch it in one pass instead of two.
    **A related, narrower case in the same table:** chaos-space-marines "Pactbound Zealots" ·
    "Marks of Chaos" Restrictions section fully confirmed via this table (3 bullets: Khorne-Psyker
    ban, Character-attach, Transport-embark) — but on the Character-attach bullet specifically,
    appdata's own table (dumped 2026-07-23, *after* a relevant errata's 20 June 2026 effective date)
    disagreed with a freshly-downloaded official Faction Pack PDF: appdata says "A CHARACTER unit",
    the PDF's own listed errata says change to "A CHARACTER/EPIC HERO unit". Decision (asked the
    user rather than picking solo, since this genuinely is a coin-flip): kept appdata's wording —
    structural extraction wins over even a fresh official PDF when the two **actively disagree**,
    as opposed to appdata being silent (where lesson 14 still says the PDF wins). Also confirmed,
    while re-checking the same enhancement-adjacent structural tables this session: `enhancement_
    bodyguard_group`(`_datasheet`) and `enhancement_required_keyword_group`(`_faction_keyword`) can
    retroactively CONFIRM (not just "plausibly infer") content previously left as an unconfirmed
    "appdata gap, kept because it seemed necessary" — e.g. adepta-sororitas' "Catechism of Divine
    Penitence" Repentia-attach clause and necrons' "Veil of Darkness" NECRONS-model-only prefix both
    resolved this way, upgrading their status from "plausible" to "structurally confirmed."
22. **A `limited_wargear_choice_set` with `miniatureId: null` may count the WHOLE unit instead of
    one sub-type — a different numeric bracket than its siblings is not automatically a mismatch,
    verify the equivalence before calling it one.** Found via `sync-wargear-options.mjs`
    (imperial-agents' Inquisitorial Agents, 2026-07-28): 3 sibling `limited_wargear_choice_set` rows
    for Eviscerator/Plasma pistol/Mystic stave are scoped to `miniatureId` = the **Inquisitorial
    Agent** miniature specifically (check `miniature.json`), so their `modelCount` brackets (0/5,
    0/10) count that sub-type only — matching the prose "for every 5 Inquisitorial Agents…". The
    Tome-skull set is the only one with `miniatureId: null` (not scoped to one miniature), so its
    `modelCount` brackets (6/11) count the **whole unit** (Agents + Gun Servitors) instead — first
    glance called this "an inconsistency inside appdata," which was wrong and unverified. Checked
    properly: given this datasheet's composition constraint (a 2nd Gun Servitor is only legal with
    10 Agents), every valid roster is either 5–9 Agents+1 Servitor (6–10 total models) or 10
    Agents+1–2 Servitors (11–12 total) — so ⌊agents/5⌋ and the "total ≥ 6 / ≥ 11" thresholds produce
    the **identical** result in every legal composition. appdata is encoding the same "for every 5
    Agents" rule via a total-model proxy that only works *because* of that specific composition
    constraint — confirmed self-consistent, not a data quirk, once actually derived instead of
    asserted. **Handling this going forward:** `sync-wargear-options.mjs` already treats a
    `miniatureId: null` `limited_wargear_choice_set` as non-erroring when the same items already
    appear in a `loadout_choice_set` for the same datasheet (see that script's own comment on the
    Tau Crisis-suit drone case it was written for) — this Inquisitorial Agents case happens to hit
    the same suppression path (Tome-skull *also* has a `miniatureId: null` `loadout_choice_set`
    entry, limit 2/dup-true, alongside the scaled `limited_wargear_choice_set`), so it already
    doesn't get flagged as an error. The general principle to remember even where that specific
    suppression path doesn't apply: before treating a `miniatureId: null` set's numbers as wrong,
    check whether it's counting the whole unit rather than one sub-type, and whether the
    datasheet's own composition constraints make that equivalent to the sub-type-scoped siblings.
23. **"Plausible naming variant" is not the same as "verified" — a first-pass triage that assumes
    instead of checking will sometimes get the *direction* of the fix backwards, and always misses
    the actually-useful evidence.** `sync-wargear-options.mjs`'s first triage pass (2026-07-28)
    called two flags "plausible naming variants" (Death Company Dreadnought's Brutalis/blood fists,
    imperial-agents' Nuncio-acquila) purely from pattern-matching ("Blood Angels reflavor things",
    "appdata sometimes has typos") without actually cross-checking either claim. Asked to verify
    properly, both turned out to be **appdata contradicting itself**, not just "a plausible
    explanation" — and the exact mechanism differs, which matters for spotting the pattern again:
    - **Nuncio-acquila**: the `wargear_item` **catalog name** has the typo ("Nuncio-**acquila**"),
      but that same item's own **ruleText** (the Designer's Note, `agents-of-the-imperium.json`
      `wargear[].ruleText`) spells it correctly ("Nuncio‐**aquila**"). Same failure mode as lesson
      2 (OCR/typo defects), just isolated to one field instead of the whole entry — check ALL of an
      item's own text fields against each other, not just its bare name, before trusting the name.
    - **Death Company Dreadnought's Brutalis fists/bolt rifles**: a **structural cross-reference**
      bug, not a spelling one — `base_miniature_loadout_wargear_option` for this datasheet points at
      the *generic* `Brutalis Dreadnought` chassis' `wargear_item` ids instead of this datasheet's
      own Blood-Angels-renamed ones, while the SAME datasheet's flat bundle (`wargear[]`, built by a
      different pipeline stage from the same source data) has the renamed ids correctly. **New
      failure class for `sync-wargear-options.mjs` specifically**: when a base-loadout item flags as
      missing on a Chapter/faction-specific *reskin* of a shared vehicle chassis, check the generic
      chassis' own datasheet in appdata for the SAME item family before assuming wh11ed is wrong —
      the join table may be pointing at the un-reskinned original.
    - Contrast with **Hekaton Land Fortress's "Panspectral Scanner"** (checked in the same pass):
      here appdata's flat bundle agreed with itself (one word) and wh11ed had the actual typo
      ("pan spectral scanner", inline in `loadout` only — the item's own name elsewhere in the same
      file was already correct) — **fixed** in wh11ed. Same surface symptom (a spelling mismatch
      flagged by the script) had two completely different resolutions on the two sides of the same
      pass — don't apply one verdict ("it's probably appdata's fault") to the whole flagged list
      without checking each one individually.
24. **A checker that only searches the RECEIVING side of a relationship can report a real thing as
    missing when the source material actually documents it on the OTHER side.** `sync-ally-inclusion
    .mjs`'s first version of the universal-rule check (2026-07-28) searched every faction that could
    *take* an ally (Space Marines, Black Templars, Astra Militarum, …) for a "can include <ally>"
    clause, found nothing in 7 of 8 cases, and concluded that content was genuinely absent from
    wh11ed — a conclusion accepted and written into the coverage plan as a real, separately-tracked
    content-authoring task ("~20-30 files, EN+RU"). It was **completely wrong**: GW publishes this
    exact kind of rule as a single named army rule on the ALLY's own codex page (Chaos Daemons'
    "Daemonic Pact", Imperial Knights' "Freeblades", Titan Legions'/Chaos Titan Legions' "Titanic
    Support", Imperial Agents' "Assigned Agents") — not copy-pasted into every book that can take it
    — and wh11ed already had all 8, verbatim, sitting on exactly those ally pages the whole time.
    Caught only because the user pushed back on taking on a large content task without first
    double-checking it was real ("исправь что из этого можешь исправить сам... подумай"), which led
    to actually opening `chaos-daemons.js`/`imperial-knights.js`/`titan-legions.js`/`imperial-agents
    .js` before writing a single line of new content — and finding the "missing" text already there.
    **General principle:** when a checker walks a directed relationship (A can include B), and the
    obvious place to look (A's file) comes up empty, check whether the *source material's own
    convention* puts the clause on the other end (B's file) before concluding it's absent — a
    one-way search only proves absence on the side actually searched. Fixed by adding a
    `resolvedOnOwnPage` pass that checks the ally's own page (resolved via `allied_faction_parent_
    faction_keyword`) before falling back to the per-receiving-faction search.
25. **Two appdata datasheets can share the same printed name but be genuinely different rows** —
    resolving an exclusion by NAME alone can silently match the wrong one. `sync-roster-
    restrictions.mjs`'s `detachment_excluded_datasheet` check for Deathwatch's "Black Spear Task
    Force" flagged 4 excluded units (Watch Master, Corvus Blackstar, Watch Captain Artemis,
    Deathwatch Kill Team) as missing from that detachment's own rule body — but `deathwatch.js`
    already has units by all 4 of those exact names. Tracing the specific `datasheetId`s back to
    `wh40k-appdata/tables/datasheet.json` (not just the per-faction bundle export) showed each one's
    `publicationId` resolves to **Codex: Imperial Agents**, not Index: Deathwatch — they're a
    different, same-named datasheet from a different codex (Imperial Agents also prints its own
    "Watch Master"/"Corvus Blackstar"/etc. for armies that ally them in), already banned wholesale
    by Deathwatch's own armyRule text ("cannot include any Agents of the Imperium Deathwatch
    units"). A literal name match across two different appdata publications produced a false
    "missing" exactly the way lesson 24's one-directional search did — a 4th false positive in the
    same investigation, all caught by re-verifying against the raw table instead of trusting the
    first plausible read (see `[[feedback_verify_dont_assert]]`). **General principle:** when a
    same-named datasheet exclusion doesn't match wh11ed's text on the expected page, check the
    excluded datasheet's OWN `publicationId`/faction bundle before concluding wh11ed is missing
    something — it may be a same-named sibling from a different codex, already covered by an
    existing broader restriction.
26. **When reconstructing expected wording from a structural join, prefer diffing against the
    source's OWN prose first — the join and the prose routinely disagree without either being
    wrong.** `sync-enhancement-restrictions.mjs`'s first version reconstructed an enhancement's
    expected "X model only" wording purely from `enhancement_required_keyword_group`'s
    `_faction_keyword`/`_keyword` join, and got **26 false positives out of 28 flags** on the first
    run. Every disagreement had an innocent explanation: GW's prose omits a keyword's containing
    faction once the keyword is already faction-exclusive ("Tech-Priest model only", no "Adeptus
    Mechanicus" — Tech-Priest doesn't exist outside that faction); the prose sometimes names a
    *different* keyword the same single datasheet also carries (Brôkhyr Iron-master's enhancement is
    grouped under keyword "Brôkhyr" in appdata, but its own prose says "IRON-MASTER" — both
    keywords sit on that one datasheet, so either identifies it); an OR-alternative group can be
    redundant because it's a strict subset of another already-listed group (Bladeguard Ancient ⊂
    Ancient — every Bladeguard Ancient already carries the Ancient keyword too); the keyword catalog
    and the prose sentence don't always agree on singular/plural ("Monster" the keyword vs "excluding
    MONSTERS models" in the prose, "Scout Sentinels" the datasheet name vs "SCOUT SENTINEL unit only"
    in the prose); and appdata's own keyword catalog carries a stray placeholder entry literally
    named "DNU" ("Do Not Use"), joined to 8 otherwise-unrelated rows across two unconnected factions
    (Necrons' C'Tan Shards, Imperial Agents' Assassins) — a data-quality artifact with no bearing on
    what the rules actually say. None of these are wh11ed bugs, and none of them are appdata bugs
    either — they're just places where the *structural join* (built for filtering/querying) and the
    *human-readable prose* (built for reading) encode the same restriction slightly differently.
    Rebuilt as a two-tier check instead: when appdata's own rules prose already states an "only"
    clause, diff wh11ed against THAT TEXT (a simple word-overlap check) rather than against the
    reconstructed join — sidesteps every disagreement above in one move, because both sides are now
    the same kind of thing (prose vs prose). Only fall back to the structural join when appdata's
    prose is *silent* about the restriction entirely (states no "only" clause anywhere) — which is
    the genuinely valuable, hard-to-find case this script exists for in the first place (see lesson
    below and `Veil of Darkness`/`Scroll of Proclamation`). **General principle:** a structural join
    table and a human-authored prose field describing the "same" fact are not guaranteed to phrase it
    identically — when both exist, diff prose-to-prose and reserve the structural reconstruction for
    when the prose has nothing to diff against at all.
27. **appdata's own prose can be completely silent about a real, structurally-encoded restriction —
    and this is genuinely rare enough that finding one is worth writing down, not assuming it's the
    only one.** Necrons' "Veil of Darkness" enhancement's `rules` text never says "NECRONS model
    only" anywhere; only the structural `enhancement_required_keyword_group_faction_keyword` row
    says so. wh11ed had been missing the prefix until an earlier session fixed it by luck (asking a
    good follow-up question, not a standing check) — the discovery that motivated building
    `sync-enhancement-restrictions.mjs` at all. Building the script surfaced a second, previously-
    unknown instance the same way: space-marines.js's "Scroll of Proclamation" was missing "Adeptus
    Astartes model only." in EN — and critically, `ru/space-marines.js`'s translation of the SAME
    enhancement already had "Только модель Adeptus Astartes." in the equivalent position. That
    means this wasn't a translation gap (RU correctly reflects the structural restriction) — it was
    a one-sided EN regression/oversight, the EN and RU copies of the same fact had drifted apart in
    exactly the direction CLAUDE.md warns is the project's most common bug class. Fixed 2026-07-28.
    **General principle:** when a checker's fallback path (structural-only, no prose to confirm
    against) flags something, check BOTH locale files before writing anything — if one locale
    already has the correct text, the fix is a one-line addition to the other, not new content.
28. **A faction with multiple distinctly-named army rules can have one of them silently
    unrepresented, because the existing text-diff script only matches candidates by NAME.**
    `sync-faction-text.mjs`'s army-rule comparison gathers appdata candidates via
    `nameRelated(en.armyRule.name, r.name)` (substring containment either direction) — this works
    fine when wh11ed's single combined `armyRule.name` is a superset string ("Oath of Moment & The
    Unforgiven" contains both "Oath of Moment" and "The Unforgiven"), but 19 factions carry a
    SEPARATE, differently-named army rule that isn't folded into wh11ed's combined name at all if
    it was ever missed during authoring. Building `sync-army-rule-coverage.mjs` to check for this
    found exactly that, twice: `space-wolves.js` was completely missing "Curse of the Wulfen" (a
    real +1/+3 Objective Control passive ability, not a wording nit — the whole ability was absent),
    and `blood-angels.js` was completely missing "The Sons of Sanguinius" (the mono-Chapter
    restriction + Designer's Note that every other Space-Marine-Chapter book has some form of).
    Neither gap had ever been flagged by any existing script, because `sync-faction-text.mjs` only
    ever compared wh11ed's whole combined body against ONE name-matched candidate at a time, and a
    completely-absent SECOND rule just never entered the comparison. **General principle:** when a
    source entity can have multiple named sub-parts that get merged into one combined field on the
    target side, a name-based comparison can silently ignore an entire sub-part if authoring simply
    never included it — check "does entity X exist somewhere in the combined field," not just
    "does the combined field match candidate X," and do it by ENUMERATING the source's sub-parts
    (not by trusting the target's own claimed structure) so a fully-missing sub-part is still
    visible.
29. **A crude word-overlap heuristic can badly under- and over-report on free-text prose, in
    opposite directions depending on vocabulary distinctiveness — treat it as a triage signal, not
    a verdict.** Building `sync-army-rule-coverage.mjs`'s check surfaced this twice in the same
    investigation. Under-report (false negative): Space Wolves' "Curse of the Wulfen" scored 78%
    word overlap against wh11ed's WHOLE faction file despite being completely absent, because its
    vocabulary ("unit", "objective", "infantry", "vehicle", "character") is common enough that most
    of those words appear elsewhere in the file for unrelated reasons — only a targeted grep for a
    distinctive multi-word phrase ("Objective Control characteristic", "Wolf Priest") actually
    proved absence. Over-report (false positive): Death Guard's "Nurgle's Gift (Aura)" scored only
    54% despite being present and correct, because each Plague's flowery italic flavour description
    ("Limbs shuddering with fever palsy, bones turned brittle as glass...") was reworded/shortened in
    wh11ed while the mechanical content matched exactly. **General principle:** a word-overlap
    percentage on free prose is a reasonable way to generate a short list of candidates worth a
    human's attention, but neither a high score proves presence (could be surrounded by unrelated
    generic vocabulary) nor a low score proves absence (could be legitimately reworded flavour text)
    — every flagged candidate still needs an actual read of both sides before a verdict, the same
    discipline `[[feedback_verify_dont_assert]]` already establishes for structural-join mismatches.
30. **A generic wargear option ("1 marker drone") can be structurally correct while the effect it
    grants is nowhere in the text — and this can hide behind a case-sensitive grep giving a false
    "already covered."** `sync-army-rule-coverage.mjs` flagged Tau Empire's "Drones" army rule
    (Shield Drone: +1 Wounds) as apparently missing from `tau-empire.js`. The first check for it —
    `grep -n "Shield Drone"` — found nothing and was briefly taken as confirmation. It was wrong:
    wh11ed writes the option in lowercase ("1 shield drone", matching how bullet-list wargear names
    are conventionally cased throughout this file), so a case-sensitive search for the capitalized
    form missed 11 real occurrences. Re-running case-insensitively (`grep -in`) found the option
    bullet present on every affected unit — but the option bullet only ever lists the drone by name
    ("1 gun drone / 1 marker drone / 1 shield drone"), never explains what any of them actually DO.
    Tracing the structural join (`loadout_choice`/`limited_wargear_choice` → `wargear_item`) to all
    11 datasheets that offer it confirmed: the "Gun Drone"/"Missile Drone" options were already fully
    correct in effect (their granted weapon — Twin pulse carbine/Missile pod — was already present in
    every affected unit's `ranged[]`, just not narrated), but "Marker Drone" (Markerlight keyword +
    Observer-even-after-Advancing) and "Shield Drone" (+1 Wounds) — and "Guardian Drone" (-1 to enemy
    Wound rolls) on the 2 units that offer it — were genuinely unexplained anywhere. Fixed by adding
    a `wargearAbilities` entry per drone type to each of the 11 datasheets (EN+RU, reusing shared RU
    constants matching this file's existing convention for repeated wargear text). **General
    principle:** (a) grep case-sensitivity is a real, easy-to-miss failure mode — default to
    case-insensitive when checking "is X mentioned anywhere," especially for lowercase-conventional
    wargear names; (b) an option existing in a bullet list doesn't mean its EFFECT is documented — a
    structural join can be satisfied by the option being selectable while the actual rules text for
    what it does is absent, and those are two different questions a checker (or a human) can
    conflate.
