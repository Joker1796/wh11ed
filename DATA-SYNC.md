# Обновление базы правил под новую версию wh40k-appdata

> **Единая точка входа.** Если тебе передали новую сборку приложения GW (APK) или просто
> сказали «вышло обновление, обнови базу знаний» — начни отсюда, независимо от того, есть
> ли у тебя память о прошлых сессиях. Файл самодостаточен.

## 0. Контекст: что такое appdata и откуда берутся находки

`wh40k-appdata` — приватный репозиторий-сосед (`../wh40k-appdata` рядом с этим), дамп
данных из официального приложения Warhammer 40,000: The App, взятый как 100%-эталонный
источник правил. `wh11ed` периодически с ним сверяется и подтягивает изменения (новые
детачменты/юниты/эрраты, исправленные очки, дрейф текста правил).

Если пользователь **положил свежий APK** (в `sources/apk/`, файл `*.xapk`/`*.apk`) — одна
команда извлекает `dump.json` и пересобирает весь appdata; ничего распаковывать руками не надо:

```bash
cd ../wh40k-appdata && node scripts/ingest.mjs   # берёт свежий пакет из sources/apk сам
```

`ingest.mjs` печатает `old data_version → new`. Если совпало — обновлять нечего. Поскольку
`tables/` и `factions/` закоммичены, **прошлая версия остаётся в git HEAD**, и регенерация —
это обозримый git-diff, а не «чёрный ящик». (Ручной путь на 4 команды всё ещё описан в
`../wh40k-appdata/README.md`.)

## 1. Что именно изменилось между версиями (дёшево, без чтения 35 МБ)

**Сначала — классифицированный дифф appdata против прошлой версии**, чтобы не гонять глазами
весь `npm run sync` и не жечь токены:

```bash
cd ../wh40k-appdata && node scripts/changes.mjs --json changes.json
```

`changes.mjs` сверяет пересобранный appdata с git HEAD **по стабильным id** и делит всё на:
`ADDED` / `REMOVED` (новые/удалённые сущности), `CHANGED — prose/errata` (изменился ТЕКСТ
правила → это и пойдёт в перевод) и `CHANGED — scalar` (очки/статы/keywords/профили — переводу
НЕ подлежат). Матчинг по id, поэтому перестановка блоков (displayOrder) не создаёт ложного
шума, в отличие от построчного диффа. `--from`/`--to` принимают любые git-ref (для ретроспекции
прошлого бампа: `--from HEAD~1 --to HEAD`).

**Потом — сверка appdata против wh11ed** (что у НАС отсутствует/разошлось):

```bash
cd ../wh11ed && npm run sync
```

Один прогон, report-only (кроме предупреждений про устаревшие сайдкары — см. §5). Список
под-проверок — в шапке `scripts/sync.mjs`. Читай его вывод, **пересекая с `changes.json`**:
трогать нужно только то, что реально поехало в этой версии, а не переаудитить все 30 фракций.
Точечно по одной фракции: `node scripts/sync-appdata.mjs <slug>` (структура/очки) и
`npm run sync:text <slug>` (проза).

## 2. Сначала план, потом правки

**Не бросайся чинить построчно.** По `changes.json` + выводу `npm run sync` сгруппируй
находки и представь пользователю короткий план ДО начала правок:
- что нового (детачменты/юниты/стратагемы/FAQ),
- где дрейф эрраты (изменился текст существующего правила),
- где структурные расхождения (очки, ключевые слова, ограничения ростера),
- что не укладывается ни в один известный паттерн ниже — это сигнал, что нужен новый
  guardrail-скрипт по образцу существующих (`scripts/sync-*.mjs`), а не разовый хак.

Это именно то, чего ждёт пользователь: он даёт команду «обнови базу» — агент сам
разбирается в объёме и докладывает план, а не молча правит 40 файлов подряд.

## 3. Классификация находок — известные паттерны

Три типа результата на каждую строку:
- `+ missing in wh11ed` — appdata содержит что-то, чего нет у нас → добавить.
- `- extra in wh11ed` — у нас есть что-то, чего нет в appdata → проверить (переименование?
  Legends? реальный false positive из списка ниже?) и поправить или задокументировать.
- `~ ... differs` — расхождение в значении (очки, CP, текст) → сверить обе стороны, не
  копировать appdata бездумно — иногда правее wh11ed (см. ниже).

### Известные ложные срабатывания (не чинить как баг)

- **Combat Patrol контент.** Публикации с `isCombatPatrol` — отдельный боксовый режим с
  0-очковыми ростерами; wh11ed matched-play-only и ничего оттуда не несёт. Скрипты уже
  фильтруют это через `combatPatrolNames()`, но если целый блок «detachment + N датащитов,
  все 0pts» вылезает как missing — почти всегда это как раз CP-бокс, не реальный пробел.
- Юникод-варианты дефиса (U+2010/U+2011) в именах appdata — `norm()` уже это схлопывает.
- `"1CP"` (wh11ed) vs `"1"` (appdata) — форматирование, не расхождение.
- Суффикс `(Aura)`/`(Psychic)` в названиях улучшений/способностей — wh11ed иногда его
  добавляет, appdata — никогда.
- MFM «copy tax» — вторая, более дорогая ценовая планка за спам одного юнита (`note:
  "1st-2nd"` vs `"3rd+"`) — у appdata в джойне видна только базовая цена; наличие ДВУХ цен
  у wh11ed корректно, не баг.
- Дублирующиеся строки цены в appdata (совпадающий `unit_composition` джойн) — де-дуп уже в
  скриптах.
- Некоторые датащиты нарочно хранят «designer's note» — редакторский текст без аналога в
  appdata; не трогать.
- У части юнитов в appdata ДВЕ цены за один и тот же состав модели (историческая MFM-планка)
  — wh11ed показывает нижнюю; не переключать на верхнюю без явного основания.
- **Если у юнита, где wh11ed раньше была ОДНА цена, вдруг появились ДВЕ** — это может быть не
  шум, а GW реально распространили copy-tax механику на новый юнит (видел на бампе 925: 9
  датащитов Space Marines). Само появление второго числа взять из appdata можно смело, но
  **текст порога** («1st-2nd»/«3rd+», формула не выводится, разный у каждого юнита) appdata не
  хранит вообще — не гуглить/качать сторонний MFM PDF, чтобы его угадать (легко нарваться на
  устаревшую версию); брать с живого сайта: `python3 scripts/scrape-mfm.py` (обновляет
  `src/data/mfm/*.js`) → `npm run sync:mfm` (аудит датащитов против них; `--write` переносит
  цифры в `src/data/datasheets/*.js`, включая `pointsOverrides` капитулов). Цены — EN-only
  данные (ru/-файлы датащитов цен не несут), парити не затрагивается.
- **5 SM-Chapter фракций** (black-templars/blood-angels/dark-angels/deathwatch/space-wolves):
  бандл appdata содержит только эксклюзивные для капитула публикации, а wh11ed
  (обоснованно) фолдит юниты, общие с `space-marines.js`. Смотреть `missing`/`differs`;
  `extra` в основном шум, кроме реальных переименований/удалений.
- **У самого appdata бывают опечатки** — не копировать «missing/extra» пару вслепую, сверить
  какая сторона реально права по-английски (пример: Blood Angels «Martial Examplars»
  вместо «Exemplars» — ошибка appdata, wh11ed был прав).
- Способности appdata с `type !== 'datasheet'` невидимы для диффа способностей на датащите
  (сверяются только `type === 'datasheet'`) — прежде чем чинить «extra ability», проверить
  сырой JSON фракции: возможно, appdata просто классифицировал её иначе (`core`/`faction`).
- **Апострофы в appdata — всегда типографские `’` (U+2019)**, никогда прямые `'`. Если
  хардкодишь строку для сравнения с именем/keyword из appdata — грепни реальное значение,
  не печатай апостроф вручную (иначе сравнение молча не сработает).
- **Осиротевший keyword `"DNU"`** (Do Not Use) — appdata-артефакт, не привязан ни к одному
  реальному требованию. Если improvement/enhancement ссылается на него как на required
  keyword — подставлять реальное per-юнитное требование, не переводить `"DNU"` как есть.
- **Регистр имён юнитов: `norm()` его не видит, а заголовок — видит.** Все сверки имён в
  `sync-appdata.mjs` шли через `norm()`, который приводит к нижнему регистру, поэтому 77 имён
  годами расходились с каноном (`Captain In Phobos Armour` против `Captain in Phobos Armour`,
  `Tech-priest Dominus` против `Tech-Priest Dominus`) и уезжали прямо в `<title>`/`<h1>`, которые
  генерит `gen-seo-routes.mjs`. С 2026-08-26 скрипт сравнивает имена И как есть — строка
  `⟲ datasheet name case differs`. Она означает настоящее расхождение, а не шум: канон — appdata.
  Единственные осознанные исключения — массивы кейвордов (кейворд печатается капсом, appdata сам
  хранит имя-кейворд тайтл-кейсом) и боксовый `Assault Force Vanguard Veteran Squad With Jump
  Packs`. Подробности — `APPDATA-SYNC-LESSONS.md`, урок 47.
- **UNIQUE-теги детачментов: MFM важнее прозы appdata.** Тег (`unique`) — конструкт самого MFM,
  и когда его страница печатает «UNIQUE TAG REMOVED», это и есть решение GW, даже если проза
  кодекса в appdata всё ещё несёт фразу «cannot be taken with another X detachment». Так было на
  бампе 931 (MFM v1.3): сняты `WAR DOGS` у Chaos Knights и `FLYBLOWN`/`ENGINES` у Death Guard —
  и поле `unique`, и фраза в теле правила. Из-за этого `sync:text` теперь вечно репортит у трёх
  детачментов «appdata has (missing in wh11ed): this detachment has the … tag» — **это осознанное
  расхождение, не чинить**. Отдельно: у World Eaters тег `ONSLAUGHT` MFM не печатал НИКОГДА (ни
  v1.2, ни v1.3) и «UNIQUE TAG REMOVED» над ним не ставил — он держится на прозе самого правила,
  поэтому его не трогали. «MFM молчит» ≠ «MFM снял».
- **Обязательная надбавка очков, замаскированная под «улучшение».** Формулировка вида «each
  `<unit>` from your army has the relevant ability… you must increase the points cost» — это
  не пик игрока, а обязательное повышение цены; иногда задублирована в `datasheet.points[]`
  вторым брекетом с тем же составом модели, но дороже.

### Полезные внутренние источники истины (не файлы appdata)

- **Атач через улучшение** («носитель может быть прикреплён к юниту X») иногда лежит
  структурно (`enhancement_bodyguard_group*`), а не в прозе `enhancement.rules` — guardrail
  `sync-enh-bodyguards.mjs` уже это ловит, смотреть его вывод при каждом bump.
- **`leader.units` списки бодигардов** — источник истины ПРОЗА правила Leader/Support
  (`rules[].rules`), НЕ структурные таблицы `datasheet_bodyguard_group*` (у них большие
  пробелы покрытия). Матчить владельца прозы по стабильному UUID (`sourceIds.json`), не по
  имени — несколько имён Leader/Support коллизятся между фракциями (Sorcerer в CSM/Thousand
  Sons, Ministorum Priest в Sororitas/AM/Agents и т.д.). Guardrail: `sync-leader-units.mjs`.
- **FAQ/эррата** генерируются из `tables/faq.json` в `src/data/factionFaq.json`
  (`npm run faq`), EN-only; RU — отдельный drop-in `factionFaqRu.json`, перевод делается
  вручную вслед (см. §4).

## 4. EN — сейчас, RU — отдельным проходом через очередь

> **Изменение процесса (было наоборот).** Раньше правило гласило «RU правь сразу вслед за EN, в
> той же находке». Теперь EN и перевод **разведены**: сначала прогоняешь все EN-правки этого
> бампа, помечая изменённые блоки в очередь, а перевод делаешь одним отдельным проходом. Так
> дешевле по токенам и не мешает структурную работу с переводческой.

**4a. Применяешь EN.** Структурные изменения (очки, статы, keywords, каркас новых сущностей)
берутся из `changes.json` механически; прозу правил применяешь ты по списку. Разметку и
конвенции см. `wh11ed/CLAUDE.md` → *Bilingual content conventions*.

**4b. Помечаешь, что требует перевода.** Не переводи инлайн — сгенерируй очередь из
`changes.json`:

```bash
npm run translate:queue        # читает ../wh40k-appdata/changes.json → TRANSLATION-QUEUE.local.json
```

В очередь попадает **только проза**: новые сущности (`new`) и изменённый текст правил
(`errata`). Scalar-изменения (очки/статы/профили) языконезависимы и НЕ переводятся — генератор
их отбрасывает. Каждая запись несёт EN-исходник и, для errata, ссылку на wh11ed-блок через
`sourceIds.json` (если маппинг не нашёлся — предупреждение, перегенерируй мост `npm run
sourceids`). Файл `TRANSLATION-QUEUE.local.json` гитигнорнут — это рабочий список одного бампа,
как `SYNC-LOG.local.md`.

**4c. Отдельный проход перевода.** Идёшь по очереди, на каждый блок: переводишь RU по конвенциям
(глоссы `[gloss:id:label]`, `**bold**` в обоих языках, ALL-CAPS keywords остаются английскими,
апострофы `’`), правишь RU-файл, сверяешь парити (счётчики блок-маркеров `▪ ◈ → ### ◆ [img:]`
совпадают EN↔RU, `**` сбалансированы) — и помечаешь готовым:

```bash
node scripts/gen-translation-queue.mjs --done <appId>
```

**Отдельно: `src/data/factionFaqRu.json` — оверлей ПО ИНДЕКСУ.** `FactionFaqView.vue` кладёт
`ru.entries[i]` поверх `en.entries[i]`, ключа между ними нет. `npm run faq` пересобирает EN-сторону
из appdata, и любой бамп вставляет/убирает записи — после этого весь хвост перевода у затронутой
фракции показывается под чужими вопросами, молча. Порядок: пересобрать EN, выровнять RU (старые
EN-записи сматчить с новыми по точному JSON, RU перенести, на новые оставить дырку), перевести
дырки. После — проверить инвариант: длины по каждой фракции совпадают и
`ru.entries[i].type === en.entries[i].type`. На бампе 931 это дало +38/−21 и вскрыло два СТАРЫХ
сдвига (см. `APPDATA-SYNC-LESSONS.md`, урок 46).

Блоки независимы, так что проход можно бить на части/распараллеливать. Гейт — в §6.

**4d. Отдельный проход модификаторов ростера.** Числовые модификаторы (`src/data/rosterModifiers/`)
выведены из ПРОЗЫ правил вручную, поэтому каждая запись пиннит хеш той прозы, из которой прочитана.
После бампа скрипт показывает, что поехало:

```bash
npm run modifiers          # обновить скелеты (ручные `effects`/`when`/`reviewed` сохраняются)
npm run modifiers:queue    # → MODIFIER-QUEUE.local.json, рабочий список этого бампа
# вычитка: правится src/data/rosterModifiers/<slug>.js
npm run modifiers:check    # гейт: ненулевой выход, пока есть stale/new/orphan/непрочитанные
```

`stale` — текст правила переписали под уже вычитанной записью, надо **перечитать** правило и
поправить `effects`; `new` — проза стала похожа на изменение характеристики, а записи нет;
`orphan` — источник исчез из appdata. Проход независим от прохода перевода, его можно бить на
части. Подробности механики — `src/components/roster/CLAUDE.md` → «Tier C».

**4e. RU-тексты инструкций вооружения — регенерация, не перевод.** `src/data/roster/ru/texts.js`
не ходит через очередь §4b и руками не правится: он целиком генерируется из EN
(`scripts/gen-roster-texts-ru.mjs`, рамочный переводчик со словарём предметов). После
`npm run roster:data` прогнать `npm run roster:texts-ru`; забыть нельзя — `npm run sync` держит
`rosterTextsRu --check` как гейт. Новая формулировка GW, которую рамки не знают, остаётся
полностью английской (fail-open, никогда не полу-перевод); просевшее в отчёте покрытие после
бампа — сигнал добавить рамку, а не ошибка.

## 5. Локальный лог сессии (страховка, не для гита)

Веди по ходу работы `wh11ed/SYNC-LOG.local.md` (гитигнорнут, никогда не коммитится и не
является механизмом хендоффа между машинами — для этого есть отдельный TODO-файл-паттерн,
см. ниже). Формат — заголовок на сессию, дальше по находке:

```markdown
## 2026-08-15 — appdata v920

- necrons: армейское правило Reanimation Protocols — "reanimates D3" → "heals D3" (эррата).
  EN: src/data/factions/necrons.js. RU: src/data/factions/ru/necrons.js. Реальный баг.
- black-templars: "extra" датащит Terminator Squad — false positive (SM-Chapter shared pool).
```

Смысл — если что-то пошло не так на середине большого bump'а (контекст оборвался, находка
оказалась спорной и её отложили), у тебя есть свой собственный след того, что уже
проверено и почему, не полагаясь на память ассистента между сессиями.

**Не путать с TODO-файлом-хендоффом** (`DATA-9NN-TODO.md` в корне репозитория) — это другой,
уже устоявшийся механизм: используется когда работа распределена между двумя машинами,
коммитится в ветку и удаляется в финальном коммите. `SYNC-LOG.local.md` — твой личный
черновик, TODO-файл — общий чеклист для обеих машин. Не смешивать.

## 6. Закрытие итерации

1. **Гейт перевода:** `npm run translate:check` — выходит с ошибкой, пока в очереди есть
   `pending`. Плюс `node scripts/parity-check.mjs` — ловит рассинхрон EN↔RU (пустой RU при
   непустом EN, разъехавшиеся блок-маркеры/скобки). Оба должны быть зелёными до коммита.
   Когда очередь пуста — удали `TRANSLATION-QUEUE.local.json` (это одноразовый список бампа).
2. `npm run modifiers:check` — зелёный (или осознанно отложенные записи; см. §4d).
3. `npx vitest run && npm run build` — оба зелёные.
4. Если `npm run sync` в начале флагнул устаревший сайдкар — перегенерировать:
   `npm run sourceids` / `npm run condkeywords` / `npm run faq` (без `--check` — пишут файл).
5. Бампнуть `APP_DATA_VERSION` в `src/data/appDataVersion.js` — в том же коммите, что и
   правки данных (это единственный маркер версии, `sync-common.mjs` его лишь ре-экспортит).
6. Коммит-конвенция: `data(9NN): <короткое описание>` (пример из прошлых bump'ов —
   `data(909): ...`). Прямые коммиты в `main` допустимы для этого вида работы (уже
   устоявшаяся практика), но подтверди с пользователем, если не уверен.
7. Если работа шла на двух машинах — см. TODO-файл-хендофф выше, не пересказ «на словах»:

## Для справки: где что лежит

- `../wh40k-appdata/scripts/ingest.mjs` — свежий APK из `sources/apk` → `dump.json` →
  `tables/`+`factions/` одной командой (§0).
- `../wh40k-appdata/scripts/changes.mjs` — классифицированный дифф по стабильным id между двумя
  версиями appdata (§1); `--json` пишет `changes.json` для генератора очереди.
- `scripts/gen-translation-queue.mjs` — `changes.json` → `TRANSLATION-QUEUE.local.json` (§4b);
  `npm run translate:queue` / `translate:check` (гейт) / `--done <appId>` (отметить готовым).
- `scripts/gen-roster-modifiers.mjs` — числовые модификаторы ростера: пишет/обновляет скелеты,
  `--check` (гейт, в `npm run sync`), `--queue` (рабочий список бампа). Хеш прозы в каждой записи —
  это то, чем модификатор привязан к тексту правила (§4d).
- `scripts/sync.mjs` — оркестратор, единая команда `npm run sync`; шапка файла перечисляет
  каждую под-проверку и что она покрывает.
- `scripts/lib/sync-common.mjs` — общие хелперы (нормализация имён, конвертация разметки
  appdata→wh11ed, мемоизированное чтение JSON, фильтр Combat Patrol контента).
- `AUDIT-PROGRESS.md` — исторический протокол одноразового полного аудита всех 30 фракций
  (завершён); часть найденных тогда паттернов уже перенесена в §3 выше, но сам файл не
  переиспользуется как процедура для регулярных bump'ов — этот документ (`DATA-SYNC.md`)
  им является.
