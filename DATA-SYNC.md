# Обновление базы правил под новую версию wh40k-appdata

> **Единая точка входа.** Если тебе передали новую сборку приложения GW (APK) или просто
> сказали «вышло обновление, обнови базу знаний» — начни отсюда, независимо от того, есть
> ли у тебя память о прошлых сессиях. Файл самодостаточен.

## 0. Контекст: что такое appdata и откуда берутся находки

`wh40k-appdata` — приватный репозиторий-сосед (`../wh40k-appdata` рядом с этим), дамп
данных из официального приложения Warhammer 40,000: The App, взятый как 100%-эталонный
источник правил. `wh11ed` периодически с ним сверяется и подтягивает изменения (новые
детачменты/юниты/эрраты, исправленные очки, дрейф текста правил).

Если `wh40k-appdata` в этом чекауте нет или он устарел — пересобери его из свежего APK по
инструкции в `../wh40k-appdata/README.md` («Regenerating from a newer app version», 4
команды, без зависимостей). После пересборки проверь версию:

```bash
node -e "console.log(require('../wh40k-appdata/tables/_meta.json').data_version)"
```

и сравни с `src/data/appDataVersion.js` (`APP_DATA_VERSION`) — если совпадает, обновлять
нечего.

## 1. Запусти сверку

```bash
npm run sync
```

Один прогон, report-only, ничего не пишет (кроме предупреждений про устаревшие сайдкары —
см. §5). Раньше это было 18 отдельных процессов; теперь один процесс с общим кэшем чтения
appdata-таблиц (`scripts/lib/sync-common.mjs`) — быстрее и одинаково по выводу. Список всех
под-проверок и что каждая покрывает — в шапке `scripts/sync.mjs`, не дублирую здесь.

Для точечной работы над одной фракцией (быстрее, чем гонять всё):

```bash
node scripts/sync-appdata.mjs <slug>       # структура/очки/переименования одной фракции
npm run sync:text <slug>                    # текстовый дифф прозы правил той же фракции
```

## 2. Сначала план, потом правки

**Не бросайся чинить построчно.** Прочитай весь вывод `npm run sync` целиком, сгруппируй
находки по темам и представь пользователю короткий план ДО начала правок:
- что нового (детачменты/юниты/стратагемы/FAQ),
- где дрейф эрраты (изменился текст существующего правила),
- где структурные расхождения (очки, ключевые слова, ограничения ростера),
- что не укладывается ни в один известный паттерн ниже — это сигнал, что нужен новый
  guardrail-скрипт по образцу существующих (`scripts/sync-*.mjs`), а не разовый хак.

Это именно то, чего ждёт пользователь: он даёт команду «обнови базу» — агент сам
разбирается в объёме и докладывает план, а не молча правит 40 файлов подряд.

## 3. Классификация находок — известные паттерны

Три типа результата на каждую строку:
- `+ missing in wh11ed` — appdata содержит что-то, чего нет у нас → добавить.
- `- extra in wh11ed` — у нас есть что-то, чего нет в appdata → проверить (переименование?
  Legends? реальный false positive из списка ниже?) и поправить или задокументировать.
- `~ ... differs` — расхождение в значении (очки, CP, текст) → сверить обе стороны, не
  копировать appdata бездумно — иногда правее wh11ed (см. ниже).

### Известные ложные срабатывания (не чинить как баг)

- **Combat Patrol контент.** Публикации с `isCombatPatrol` — отдельный боксовый режим с
  0-очковыми ростерами; wh11ed matched-play-only и ничего оттуда не несёт. Скрипты уже
  фильтруют это через `combatPatrolNames()`, но если целый блок «detachment + N датащитов,
  все 0pts» вылезает как missing — почти всегда это как раз CP-бокс, не реальный пробел.
- Юникод-варианты дефиса (U+2010/U+2011) в именах appdata — `norm()` уже это схлопывает.
- `"1CP"` (wh11ed) vs `"1"` (appdata) — форматирование, не расхождение.
- Суффикс `(Aura)`/`(Psychic)` в названиях улучшений/способностей — wh11ed иногда его
  добавляет, appdata — никогда.
- MFM «copy tax» — вторая, более дорогая ценовая планка за спам одного юнита (`note:
  "1st-2nd"` vs `"3rd+"`) — у appdata в джойне видна только базовая цена; наличие ДВУХ цен
  у wh11ed корректно, не баг.
- Дублирующиеся строки цены в appdata (совпадающий `unit_composition` джойн) — де-дуп уже в
  скриптах.
- Некоторые датащиты нарочно хранят «designer's note» — редакторский текст без аналога в
  appdata; не трогать.
- У части юнитов в appdata ДВЕ цены за один и тот же состав модели (историческая MFM-планка)
  — wh11ed показывает нижнюю; не переключать на верхнюю без явного основания.
- **5 SM-Chapter фракций** (black-templars/blood-angels/dark-angels/deathwatch/space-wolves):
  бандл appdata содержит только эксклюзивные для капитула публикации, а wh11ed
  (обоснованно) фолдит юниты, общие с `space-marines.js`. Смотреть `missing`/`differs`;
  `extra` в основном шум, кроме реальных переименований/удалений.
- **У самого appdata бывают опечатки** — не копировать «missing/extra» пару вслепую, сверить
  какая сторона реально права по-английски (пример: Blood Angels «Martial Examplars»
  вместо «Exemplars» — ошибка appdata, wh11ed был прав).
- Способности appdata с `type !== 'datasheet'` невидимы для диффа способностей на датащите
  (сверяются только `type === 'datasheet'`) — прежде чем чинить «extra ability», проверить
  сырой JSON фракции: возможно, appdata просто классифицировал её иначе (`core`/`faction`).
- **Апострофы в appdata — всегда типографские `’` (U+2019)**, никогда прямые `'`. Если
  хардкодишь строку для сравнения с именем/keyword из appdata — грепни реальное значение,
  не печатай апостроф вручную (иначе сравнение молча не сработает).
- **Осиротевший keyword `"DNU"`** (Do Not Use) — appdata-артефакт, не привязан ни к одному
  реальному требованию. Если improvement/enhancement ссылается на него как на required
  keyword — подставлять реальное per-юнитное требование, не переводить `"DNU"` как есть.
- **Обязательная надбавка очков, замаскированная под «улучшение».** Формулировка вида «each
  `<unit>` from your army has the relevant ability… you must increase the points cost» — это
  не пик игрока, а обязательное повышение цены; иногда задублирована в `datasheet.points[]`
  вторым брекетом с тем же составом модели, но дороже.

### Полезные внутренние источники истины (не файлы appdata)

- **Атач через улучшение** («носитель может быть прикреплён к юниту X») иногда лежит
  структурно (`enhancement_bodyguard_group*`), а не в прозе `enhancement.rules` — guardrail
  `sync-enh-bodyguards.mjs` уже это ловит, смотреть его вывод при каждом bump.
- **`leader.units` списки бодигардов** — источник истины ПРОЗА правила Leader/Support
  (`rules[].rules`), НЕ структурные таблицы `datasheet_bodyguard_group*` (у них большие
  пробелы покрытия). Матчить владельца прозы по стабильному UUID (`sourceIds.json`), не по
  имени — несколько имён Leader/Support коллизятся между фракциями (Sorcerer в CSM/Thousand
  Sons, Ministorum Priest в Sororitas/AM/Agents и т.д.). Guardrail: `sync-leader-units.mjs`.
- **FAQ/эррата** генерируются из `tables/faq.json` в `src/data/factionFaq.json`
  (`npm run faq`), EN-only; RU — отдельный drop-in `factionFaqRu.json`, перевод делается
  вручную вслед (см. §4).

## 4. Правило: RU правится сразу вслед за EN

**Как только правишь оригинал (EN) по находке из `npm run sync` — в ТОЙ ЖЕ находке, не
батчем в конце, переведи и поправь RU.** Не оставляй «переведу все сразу потом» — это и есть
механизм, из-за которого правки расходятся (см. `wh11ed/CLAUDE.md` → *Bilingual content
conventions* за конвенциями: глоссы `[gloss:id:label]`, `**bold**` в обоих языках, ALL-CAPS
keywords остаются английскими, апострофы `’`). После каждой пары EN+RU — свериться, что
структурный парити не сломан (счётчики блок-маркеров `▪ ◈ → ### ◆ [img:]` совпадают между
`en`/`ru`, `**` сбалансированы).

## 5. Локальный лог сессии (страховка, не для гита)

Веди по ходу работы `wh11ed/SYNC-LOG.local.md` (гитигнорнут, никогда не коммитится и не
является механизмом хендоффа между машинами — для этого есть отдельный TODO-файл-паттерн,
см. ниже). Формат — заголовок на сессию, дальше по находке:

```markdown
## 2026-08-15 — appdata v920

- necrons: армейское правило Reanimation Protocols — "reanimates D3" → "heals D3" (эррата).
  EN: src/data/factions/necrons.js. RU: src/data/factions/ru/necrons.js. Реальный баг.
- black-templars: "extra" датащит Terminator Squad — false positive (SM-Chapter shared pool).
```

Смысл — если что-то пошло не так на середине большого bump'а (контекст оборвался, находка
оказалась спорной и её отложили), у тебя есть свой собственный след того, что уже
проверено и почему, не полагаясь на память ассистента между сессиями.

**Не путать с TODO-файлом-хендоффом** (`DATA-9NN-TODO.md` в корне репозитория) — это другой,
уже устоявшийся механизм: используется когда работа распределена между двумя машинами,
коммитится в ветку и удаляется в финальном коммите. `SYNC-LOG.local.md` — твой личный
черновик, TODO-файл — общий чеклист для обеих машин. Не смешивать.

## 6. Закрытие итерации

1. `npx vitest run && npm run build` — оба зелёные.
2. Если `npm run sync` в начале флагнул устаревший сайдкар — перегенерировать:
   `npm run sourceids` / `npm run condkeywords` / `npm run faq` (без `--check` — пишут файл).
3. Бампнуть `APP_DATA_VERSION` в `src/data/appDataVersion.js` — в том же коммите, что и
   правки данных (это единственный маркер версии, `sync-common.mjs` его лишь ре-экспортит).
4. Коммит-конвенция: `data(9NN): <короткое описание>` (пример из прошлых bump'ов —
   `data(909): ...`). Прямые коммиты в `main` допустимы для этого вида работы (уже
   устоявшаяся практика), но подтверди с пользователем, если не уверен.
5. Если работа шла на двух машинах — см. TODO-файл-хендофф выше, не пересказ «на словах»:
   TODO-файл авторитетнее устного пересказа объёма сделанного.

## Для справки: где что лежит

- `scripts/sync.mjs` — оркестратор, единая команда `npm run sync`; шапка файла перечисляет
  каждую под-проверку и что она покрывает.
- `scripts/lib/sync-common.mjs` — общие хелперы (нормализация имён, конвертация разметки
  appdata→wh11ed, мемоизированное чтение JSON, фильтр Combat Patrol контента).
- `AUDIT-PROGRESS.md` — исторический протокол одноразового полного аудита всех 30 фракций
  (завершён); часть найденных тогда паттернов уже перенесена в §3 выше, но сам файл не
  переиспользуется как процедура для регулярных bump'ов — этот документ (`DATA-SYNC.md`)
  им является.
